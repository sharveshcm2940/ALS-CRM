# Access and operational security

The browser is not a security boundary. Express authenticates the JWT signature, issuer, audience and expiry, checks the session and current active account in MySQL, and loads current role grants for every protected request. Temporary credentials grant access only to session and password-change routes. There is no shared login, localStorage token, client-side password, wildcard CORS, SQL string interpolation of user-controlled values, or raw database error response.

Query services apply role/record scopes to details, lists, updates, comments, dashboards, search, reports and exports. Engineers are limited to assigned tasks, accessible project memberships and invited/organized meetings. Board users cannot see confidential projects, linked tasks/meetings, or confidential customers/leads. Announcements enforce audience. Notifications are generated only after checking the recipient's module grant and record access. Settings, grants, audits and accounts additionally require CEO role. Roles are single-valued, so no user_roles table is necessary.

Strict schemas reject unknown fields, including attempts to add roles or reassign tasks through engineer progress updates. Transactions group mutations with audit events, membership changes, conversions and session revocation. Audits store action summaries, actor IDs and record IDs, never passwords, cookies, signing keys or submitted credentials. Database administrators retain operational access and are a separate trust boundary. Migrations are versioned; MySQL DDL is not transactional, so back up and recover a partially failed initial migration before retrying.

The supplied rate limiter runs in memory: 15 login attempts per IP per 15 minutes, eight failed attempts per normalized account per 15 minutes, plus a general API request cap. Use a shared store and explicitly trusted proxy configuration for horizontally scaled production. These are throttles, not permanent account lockouts. CSRF cookie/header matching and Origin validation protect state changes; SameSite=Strict and production Secure/HttpOnly session cookies further constrain browser access. Production requires HTTPS.

Development `.env`, temporary credentials, SQL dumps and database volumes are sensitive local artifacts excluded from Git. Do not publish them as public build assets. Rotate credentials when moving to production. Keep initial and reset credential delivery private, delete delivery files after use, and verify contact addresses independently. No email reset delivery or third-party integration is configured.

Deploy behind approved HTTPS and database network controls. Apply infrastructure TLS, backups, monitoring, audit retention and disaster-recovery policy. No production host, verified company domain, email addresses or infrastructure credentials were supplied, so deployment and real-user credential delivery remain operator actions. The automated checks establish application behavior in this development environment; they are not an independent penetration test or proof of a production deployment.
